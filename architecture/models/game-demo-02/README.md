# GameDemo02 候选业务模型

本目录只保存 Architecture Explorer 的业务解释层，不改变游戏源码或原始语义索引。系统名称、主要归属和流程均是人工整理的候选定义，初始 `reviews` 为空。静态确认的原始调用与读写关系，并不确认业务归属，也不证明运行时执行顺序。

当前模型包含六个业务候选：账号与宗门访问、资源生产与设施、人员与培养、灵脉探索与解锁、工坊装备与战前配置、掌门斗法。另设共用技术支撑与独立旧试验两个组。20 个模块跨越 C# 客户端与 Python 服务端；文件夹和程序集保留在独立的技术视角。

`sect_rules.command`、`settle` 等跨业务函数仅作为 participant/shared 关联，不分配多个 owner。尚不能明确职责的源码继续待分类；这比把所有文件强行分到六个系统更可靠。系统关系只汇总已有原始关系，并可回查所有成员。

## 两条流程

- **领取积存收益**：展示客户端领取回调、请求准备、HTTP 协议边界、服务端结算/领取分支、存储与响应、客户端提交状态及资源标签。5 段为真实静态调用，1 段为同一个 `Request` 方法内解码之后的 `PrepareResponse` 调用位置，其余 9 段保留未验证。后者仅在合法 full 响应且没有提前返回的条件下具有源码顺序支持。
- **开始斗法 → 后续轮询固定步推进 → 结算奖励/解锁/同步 UI**：展示开始请求、创建战斗、后续独立请求推进、固定步模拟、终局分支与客户端显示。5 段为真实静态调用，其余 13 段保留未验证。后续轮询不是 `battle_start` 同一请求内的连续调用。

Python 跨模块导入调用在当前分析器中有依据但可信度为 inferred，流程没有将其升级成静态确认。HTTP 实际传送、用户操作、多个请求间的因果和 UI 最终运行效果均未经过运行时验证。字段/字典读写文字解释也不等同于已验证的跨进程数据流。

## 证据与验收

188 个锚点来自当前索引内 35 个真实源文件，使用相对路径、索引内容 SHA-256、精确行号和保留缩进的完整行 quote。源码变化后应重新索引并人工核对模型；不得仅修改哈希来掩盖语义变化。尚未明确归属的文件不需要为了覆盖率补规则。

在工具根目录执行：

```powershell
node node_modules/tsx/dist/cli.mjs --test tests/architecture-game-model.test.ts
node node_modules/tsx/dist/cli.mjs Tools/validate-architecture.ts --project game-demo-02 --worktree primary
```

验证器从 `config/local.json`（或 `EXPLORER_CONFIG` / `--config`）读取授权目录，使用已有 `lastgood.json` 做纯投影，仅重新读取锚点源码。它不启动服务、不扫描全项目、不执行目标程序或 Git 命令、不取得索引写锁。报告写入工具缓存 `validation-architecture-<project>-<worktree>.json`，包含每个锚点的当前内容/字节哈希、流程证明、归属复核状态及聚合关系验证结果。人工复核后的模型仍可验证，CLI 不要求 reviews 永远为空。

初始验收的 6,601 个未分类源码实体会明确报告，其中包含尚无唯一 owner 的字段、参数、局部数据和共享组件，不代表 6,601 个独立业务组件。具体数值随源索引变化。
