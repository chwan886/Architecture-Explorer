三、接收和扫描的实际实现

1. 工作流只允许工具 main；在请求跨仓库凭据前校验 main protected、版本、固定 repo/ref、SHA、来源 run/attempt/URL 与配置前提。

3. Tools/ci-authorize.ts 查询指定 run 的指定 attempt 及其 jobs，不取 latest：repository/event=push/head_branch=main/head_sha/path/run_attempt 必须匹配，全部确认的 Fast/tools jobs 已成功；来源整体可以仍在发送中，失败/取消不接受。
4. 核对双方 main 保护与历史、必需检查 context；双方均要求 Code Owner，游戏还要求过期批准处理、最近 push 独立批准、strict 最新检查与解决讨论。聚合全部有效 Ruleset 的数量最大值与各布尔门禁，不因分散到不同规则或返回顺序误判。
5. 查真实已合并 PR：merge_commit_sha=source_sha，base 是固定游戏 main；分页读取合并前、准确 PR head、非作者、非 bot 的 User 批准，独立不同用户数量须达到游戏实际有效审批门限。普通 COMMENTED 不撤销批准；自审、撤销、要求修改、旧 head、合并后补审不能通过。工具侧此处核对当前平台规则，不声称已核验工具 PR 审批数量。
6. 游戏 checkout 的 ref 始终是 source_sha，fetch 完整历史；严格 Git 再证实 HEAD 非空、origin 固定、属于 origin/main 历史、工作区与未跟踪文件干净。
7. Tools/ci-references.ps1 仅取人工批准的 SHA256 固定 HTTPS 元数据 ZIP，不跟随跳转，仅允许根 references.json 和 DLL，拒绝路径穿越、目录、链接、重名或指纹错误。
8. Tools/ci-snapshot.ts 生成 runner 临时配置，引用和缓存/输出均在工具侧；Unity 清单版本必须匹配游戏 ProjectVersion.txt，每 DLL 摘要核对，至少 CoreModule，禁止根聚合 UnityEngine.dll 混用和假 Unity 类型。

10. 扫描前后核对游戏 HEAD、完整 Git 状态、授权源文件字节摘要、工具 tracked 差异和人工模型原字节。待复核职责/解释/锚点保留，不确认、不重写、不刷新人工哈希。
